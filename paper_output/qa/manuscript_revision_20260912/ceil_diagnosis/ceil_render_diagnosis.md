# 上取整符号显示成斜杠的独立诊断

已实际查看 revision_v2 第27页：内联上取整式和式(35)的左右符号均呈斜杠状。PDF文本抽取仍得到正确的 U+2308/U+2309，因此不能用文本提取替代这项视觉检查。

DOCX 中字符本身没有被改成斜杠，而是普通 m:r 中的 ⌈/⌉，设置了 m:sty=p、Times New Roman 和直立字体属性，但没有 m:nor。不能仅凭外观把原因断定为字库缺字；独立小样表明，改变 OMML 正常文字标志能解决问题，换字体本身不能解决。

| 5页小样的实际方案 | 实际视觉结果 |
|---|---|
| 第1页：当前原样 | 成功复现缺陷 |
| 第2页：仅在符号 m:rPr 内增加 m:nor=1 | 内联和显示式均呈正确上取整符号 |
| 第3页：仅将符号字体改成 Cambria Math | 缺陷仍在 |
| 第4页：仅移除符号 w:rPr | 缺陷仍在 |
| 第5页：改为原生 m:d ceiling 括号结构 | 缺陷仍在 |

最小可用修复是在 mathematical_style 完成后，仅给 m:t 为 ⌈ 或 ⌉ 的 m:r 添加 `<m:rPr><m:nor m:val="1"/></m:rPr>`。不改变字符、参数、数值、上下标或分式。也可以在主脚本 token 循环中，将 `token in {'⌈','⌉'}` 加入设置 m:nor=1 的条件。纯函数样例见 ceil_fix_snippet.py，它不会自行打开或保存任何稿件。

建议覆盖全稿同类符号：正文式(12)、附录内联式和式(35)均有上取整字符。最终仍需对修复后的正式PDF做视觉复核。

小样来源是正在编排的DOCX，此时其哈希已不同于 revision_v2 的源文件；两者的绑定信息均记录在 JSON。小样第1页重新复现了 revision_v2 的可见缺陷。此次仅创建独立 QA 小样与诊断报告，未改主稿或主构建脚本。
