## 2. 三个原发现的闭环

| 原发现 | v6 实际实现 | 独立判断与验证性质 |
|---|---|---|
| DS01：SciPy 对 exact method class 的判定令 DiskBDF 子类默认选用另一侧多项式，accepted 断点可能有末位差 | `align_bdf_segments(result)` 用相同的 `result.sol.ts` 和同一组 `result.sol.interpolants` 重建 `OdeSolution(..., alt_segment=True)`；core 在每个主段及事件后的 tail 都调用 | 根因已对应修复。重新选择现有多项式不改系数，不重新积分，也不改事件结果。既有 v6 全部内部断点实跑检查为零差 |
| DS02：收敛驱动的后处理抛错时，Run 没有统一 finally close | 每轮网格先 `run=None`，求解、保存、投影、警告检查、网格比较、解析比较和报告写出均处于同一个 try 内；finally 中只要 Run 已返回就关闭 | 原遗漏的后处理路径已纳入清理。Run 尚未返回的求解失败由 core 自身清理负责。此次为静态覆盖检查，没有宣称做过故障注入 |
| DS03：accepted memmap 完成写入后才登记，写入或 flush 失败时映射可能未被缓存清理接管 | `open_memmap` 成功返回后立即 `accepted_arrays.append(mapped)`，再写入和 flush；缓存初始文件打开失败时清理新建目录；core 清理再次出错以 `error.add_note` 附着到原异常 | 原指定的未登记窗口已修复，原求解异常也不会被 cleanup 异常替换。正常生命周期的真实三例缓存清理均成功；磁盘损坏、权限突变等失败情景未做新故障注入 |

`DenseCache` 还将父缓存路径先 `resolve()`，再确认其位于本项目根路径内。路径固定为项目 `tmp/cache/solver_runs`；每次创建私有 `bdf_...` 目录，清理只处理该目录下的普通文件，拒绝意外目录、符号链接或不符合私有路径约定的目标。该改动符合本工作区缓存边界，不涉及原始输入、已保存结果或正式稿件。

正常关闭仍按文件句柄、accepted 映射、缓存文件、私有目录的次序释放；重复正常 close 无操作。遇到真实 I/O 错误时不能承诺操作系统一定成功删除缓存，但异常应保留并可追踪。此限制不是仍待填补的原 DS03 登记缺口，也不能据正常通过记录虚称已经验证所有故障路径。

准确口径是“这些完整 N40 轨迹的已接受步和已列查询完全相同”，不能扩大成有限测试证明所有连续时间、任意状态或未来 SciPy 版本都逐位相同。特别是本组测试不是 Q23/Q4 全程每秒空间精度证书：它是存储路径一致性证书。Q23/Q4 高网格逐秒比较另有各自收敛记录，不能混合计数。

N40 Q1 的 `diagnostics()` 所列最大质量残差在 memory/disk 间可以有 1e-15 量级差别，尽管 accepted 状态和查询相同；其数组布局与归约运算顺序会影响浮点求和。该检查承诺的是原状态/插值等价，不是所有后续归约统计值逐位相同。两者均在原质量检查容限内，这一点不否定表中的真实零状态差。

## 4. 存储和生命周期的物理数值含义保持不变

`DiskBDF` 仅覆盖 `_dense_output_impl`，由原 BDF 生成每一步稠密多项式，然后保存实际 `D` 的 float64 字节，并复制该多项式的 `t_shift`、`denom` 等定位信息。求值仍调用安装版本 SciPy 的原 `BdfDenseOutput._call_impl`。本版对断点选择的修正使用原分段器 `OdeSolution`；没有新增二次拟合、时间采样近似或空间插值。

core 原有的 4 小时环境延拓分段、事件定位与事件后复核 tail 仍按原规则执行；磁盘存储没有增加新的重新启步位置，也没有改变 BDF 的误差容限、时间步、Jacobian 或物理右端项。表中的 accepted 步、状态、事件完全相同为这一判断提供了实际证据。

accepted 数组被映射前，后段初值已经从当前末状态 `.copy()` 取出，避免后续缓存关闭影响积分初值。`save_run` 的逐块导出和 `diagnostics` 的逐块质量检查仍以同一时刻的完整温度、水分、累计失水计算；冻结 v5 审查关于 T/C 交错拆分、`2w` 权重和时间块拼接的判断未因本次修正而改变。

本次没有新增物理方程，原 E9+M55+K3+A8+J26=101 公式块登记保持不变。存储正确性同样不修复经验密度、湿空气—材料平衡水分映射、潜热和外生收缩的原物理闭合限制。

## 5. 新生产入口与来源发布时序的附加静态审查

这里的“发布”指项目内全局结果契约与 `run_manifest.json` 的生效，不是对外发送消息或公开仓库。

已核对入口的关键次序：父进程以不可重用的版本目录登记启动快照与命令；worker 校验启动 token、配置以及源码/输入/运行环境，完成真实求解、live Run 导出复核和图表后，仅写该版本目录下的契约和 `worker_success.json`。Q2/Q3 共用同一 Q23 Run，所有依赖它的导出与指标完成后再关闭；外层 finally 还清除绑定 close 方法对 Run 的引用，顺序上没有同时保留前后两条大型 Run。

生产父进程通过 `subprocess.Popen` 的真实 `wait()` 取得退出码，并保存合并 stdout/stderr 和 `process_result.json`；退出非零不会进入发布。退出为零之后仍须检查启动快照与 worker 返回证据一致、重新核对源/输入/输出哈希、验证指标证据路径，再调用发布函数。因此没有把 worker 写出的“计算成功”文本直接充当整个子进程已经退出成功。

发布在独占锁内进行：先备份旧全局文件并把旧 manifest 置为 `PUBLISHING`，再原子写各项契约，实际重读并核对输出和输入哈希，最后写新的 PASS manifest；异常分支保留失败信息并恢复旧契约，旧 manifest 最后恢复。消费者仍需检查 manifest 状态及其记录的哈希，不能只看某个结果 JSON 存在。这种顺序避免在新契约尚未全部写好时保留一个表面有效的旧 PASS。

版本清单区分“源码库存”与“实际导入模块”，检查入口及 provenance 模块加载时的源码哈希，记录命令、运行环境、字体与输入来源；没有把目录中每个 Python 文件都声称为本轮实际执行。`--review` 为 Visual Studio 的单进程求解入口，输出明确保持 GUI 观察和人工审查待确认，不自报实际进程退出，也不进入生产全局发布。

上述生产入口判断仅来自本次读取所列哈希版本的静态时序；没有额外运行大生产、故障测试或 GUI 操作。主代理应继续以本轮真实生产退出记录、最终输出验证及 GUI 观察完成相应状态，本续篇不提前替它们标记 PASS。
